# Independent adversarial review — partitio

**Date:** 2026-09-25
**Scope:** `PartitioRouterV2`, `GaslessEntry`, `OracleGuard` as deployed against Robinhood Chain 4663.
**Reviewer position:** no prior exposure to this codebase; `docs/FINDINGS.md` was deliberately not
read so the conclusions here are arrived at independently.
**Production code was not modified.** Everything added lives in `test/review/`, `test/fuzz/`,
`script/review-run.sh` and this file.

---

## 1. Method

Read `src/v2/*` line by line, then attacked each class the brief names with a deterministic
reproduction on a fork of 4663, plus a 500k-call Medusa campaign against a self-contained harness.

**A note on what "PoC test" means here.** Each PoC asserts the *vulnerable* behaviour and therefore
**passes today**. That is deliberate: it pins the bug so the assertion flips the moment the bug is
fixed. Treat "this test starts failing" as the acceptance criterion for each fix. The Medusa
properties are the other form — they are written as the intended invariant and genuinely **fail**.

### Reproducing

```bash
cd /Volumes/D/partitio-review && ./script/review-run.sh --match-path 'test/review/*'
```

`script/review-run.sh` re-pins to `head-60` on every invocation. This is not optional: the canonical
4663 RPC is not an archive node and serves roughly 90 minutes of state, so a hard-coded pin dies
mid-review (it did, once, during this one).

```bash
cd /Volumes/D/partitio-review && medusa fuzz
```

**Full suite at the time of writing: 92 tests, 92 passed, 0 failed** (17 suites, fork pin
`head-60`, forge 1.8.1, solc 0.8.26, OZ 5.1.0). 38 of those 92 are new.

### R-01 — Critical — one wei permanently bricks GaslessEntry

`GaslessEntry.fill` closes each output with ([`GaslessEntry.sol:182`](../src/v2/GaslessEntry.sol#L182)):

```solidity
IERC20(o.outputs[i].token).safeTransfer(o.owner, outs[i]);
uint256 left = IERC20(o.outputs[i].token).balanceOf(address(this));
if (left != 0) revert DustLeftBehind(o.outputs[i].token, left);
```

The check assumes the contract's balance of an output token is always exactly what this fill
produced. An ERC20 balance can be raised by anyone, at any time, for free. `GaslessEntry` has **no
owner, no sweep, no rescue and no pause**, so a single wei sent by any address makes every
subsequent order naming that token revert — permanently, for every user, at every size, on both the
router path and the aggregator path. The only remedy is to redeploy and migrate.

Attacker cost: 1 wei plus gas. Attacker privilege: none.

**PoC** — `test/review/R01_DustDoS.t.sol`
- `test_R01_oneWeiOfAaplBricksEveryAaplOrderForever` — fills a normal order, transfers 1 wei of
  AAPL from an unrelated address, shows the next fill reverts `DustLeftBehind(AAPL, 1)`, then scans
  the deployed bytecode to confirm no `owner()`, `sweep(address)` or `rescue(address,uint256)`.
- `test_R01_dustAlsoBricksTheAggregatorPath` — the relayer cannot route around it.
- `test_R01_duplicateOutputTokenIsUnfillable` — the same root cause makes any order that names one
  token in two outputs unfillable, because output 1's proceeds are already held when output 0's
  dust check runs.

**Suggested fix (not applied).** Stop treating a non-zero residual balance as an error. Measure each
output by balance delta across its own leg and forward exactly that delta, letting any pre-existing
balance sit harmlessly:

```solidity
uint256 before = IERC20(out.token).balanceOf(address(this));
// ... route ...
uint256 delta = IERC20(out.token).balanceOf(address(this)) - before;
IERC20(out.token).safeTransfer(o.owner, delta);
```

If the intent of `DustLeftBehind` was to catch an accounting bug, make it an event, not a revert.

### R-02 — High — the oracle guard does not exist on the aggregator path

`GaslessEntry`'s header states:

> The user's `minOut` and the oracle guard are enforced on the final balance either way, so a
> hostile or stale aggregator route degrades the price at worst and cannot steal.

`OracleGuard` is only ever reached from inside `PartitioRouterV2.swapExactIn`
([`PartitioRouterV2.sol:161`](../src/v2/PartitioRouterV2.sol#L161)). `_fillSingle` returns before
touching the router ([`GaslessEntry.sol:250`](../src/v2/GaslessEntry.sol#L250)):

```solidity
if (got >= out.minOut && spent <= spendable) {
    return (got, true);
}
```

So on the aggregator path the **only** check is the signed `minOut`. Nothing requires `minOut` to be
non-zero — and every shipped test in `test/GaslessEntry.t.sol` signs `minOut = 0`.

`fill` has no access control, so "the relayer" is anyone who sees the signed order. The aggregator
allowlist is immutable and holds real routers, but **`route.callData` is entirely relayer-chosen**,
and a real aggregator takes its destination from calldata.

Measured on a fork at the live AAPL price:

| | |
|---|---|
| oracle value of the 995 USDG routed | 2.942948666081229013 AAPL |
| delivered to the signer | **0** |
| taken by the relayer | 1000 USDG (the whole order) |
| result | `fill` **succeeded** |

With a non-zero `minOut` the relayer simply delivers exactly `minOut` and keeps the rest; the
extraction above `minOut` is unbounded and the 20% ceiling in `OracleGuard` never applies. The PoC
delivers 0.0294 AAPL where the *widest floor the library permits* is 2.354 AAPL — an 80x shortfall,
accepted.

**PoC** — `test/review/R02_AggregatorGuardBypass.t.sol`
- `test_R02_aggregatorPathTakesEverythingWhenMinOutIsZero`
- `test_R02_skimEverythingAboveMinOutBelowAnyPermittedBand`
- `test_R02_control_routerPathRejectsTheSameShortfall` — the identical economic shortfall on the
  router path reverts. Same economics, opposite outcome, decided only by which branch ran.
- `test_R02c_zeroFillIsAcceptedAsAnAggregatorFillWhenMinOutIsZero` — with `minOut == 0`,
  `got >= out.minOut` is `0 >= 0`, so a no-op aggregator call is *accepted* as a successful
  aggregator fill and the advertised same-transaction fallback never runs.

The mock aggregator models relayer-chosen calldata on a real router. It is a faithful model of the
capability, not of any specific Kyber selector — see §6 for what that does and does not establish.

**Suggested fix (not applied).** Run the guard on the aggregator path too, on the same final
balance:

```solidity
if (got >= out.minOut && spent <= spendable) {
    OracleGuard.enforce(out.guard, spent, got,
        IERC20Metadata(o.tokenIn).decimals(), IERC20Metadata(out.token).decimals());
    return (got, true);
}
```

Independently, reject `minOut == 0` at signing time, or require the band to be the binding floor.
The header comment should not claim a property the code does not have.

### R-03 — Medium — `spent` is measured while the fee is still held

[`GaslessEntry.sol:247`](../src/v2/GaslessEntry.sol#L247):

```solidity
uint256 spent = spendable - IERC20(o.tokenIn).balanceOf(address(this));
```

At this point the contract still holds the fee — it is not paid out until line 187. With `c` the
amount the aggregator consumed, the balance is `amountIn - c`, so

```
spent = (amountIn - fee) - (amountIn - c) = c - fee
```

Two consequences:

1. **`c < fee` underflows** and reverts the whole fill, instead of falling back to partitio. Any
   aggregator call that succeeds while consuming less than the fee — a partial route, a no-op —
   bricks that fill.
2. The guard `spent <= spendable` is checking `c <= amountIn`, not `c <= spendable`, so it does not
   do what it reads as. Today the mistake is masked, because an aggregator that eats into the fee
   makes the `safeTransfer(msg.sender, fee)` at line 187 revert anyway.

**PoC** — `test_R03_successfulAggregatorThatConsumesNothingUnderflows` (panic 0x11), with
`test_R02c_...` as the `fee == 0` control that pins the cause on the fee term.

**Suggested fix (not applied).** Snapshot the balance before the aggregator call and subtract:

```solidity
uint256 inBefore = IERC20(o.tokenIn).balanceOf(address(this));
(bool ok,) = route.aggregator.call(route.callData);
uint256 spent = inBefore - IERC20(o.tokenIn).balanceOf(address(this));
```

### R-04 — Medium — the relayer chooses how much of the order is actually routed

[`GaslessEntry.sol:222`](../src/v2/GaslessEntry.sol#L222):

```solidity
IERC20(tokenIn).forceApprove(address(ROUTER), amountIn);
uint256 got = ROUTER.swapExactIn(tokenIn, out.token, legs, out.guard, 0, address(this), ...);
```

`amountIn` is only the **approval ceiling**. `PartitioRouterV2` derives what it pulls from
`sum(legs[i].amountIn)`, and `legs` lives in the relayer-supplied `Route`, which the order signature
does not cover. So `amountIn` and `weightBps` are upper bounds the relayer may undershoot at will.

The oracle guard cannot see this, because it is evaluated against what was routed, not against what
was signed.

Measured: a signed 1000 USDG order, `maxFee` 5 USDG. The relayer routes 1 USDG, keeps the full
5 USDG fee, returns 994 USDG as "dust", and the order's replay slot and EIP-3009 authorization are
both consumed — so the signer pays a 5 USDG fee to buy 1 USDG of stock and must sign again.

**PoC** — `test_R04_relayerKeepsMaxFeeWhileRoutingOneThousandthOfTheOrder`

**Suggested fix (not applied).** Require the router to have consumed the intended amount:

```solidity
uint256 inBefore = IERC20(tokenIn).balanceOf(address(this));
uint256 got = ROUTER.swapExactIn(...);
require(inBefore - IERC20(tokenIn).balanceOf(address(this)) >= (amountIn * MIN_FILL_BPS) / 10_000);
```

or make `fee` proportional to what was actually routed rather than a free choice under `maxFee`.

### R-05 — Medium — `_legsFor` discards the output index, so baskets cannot be filled

[`GaslessEntry.sol:215`](../src/v2/GaslessEntry.sol#L215):

```solidity
function _legsFor(Route calldata route, uint256) internal pure returns (PartitioRouterV2.Leg[] calldata) {
    return route.legs;
}
```

The unnamed `uint256` is the output index, and it is thrown away: every output in a basket is routed
through the same leg set. `PartitioRouterV2._execute` checks `tokenIn` against the venue but **never
checks `tokenOut`**, so a leg for a different stock executes happily and its proceeds land in the
router while the declared output's balance delta stays zero.

There is no `Route` that fills a two-output basket. All three candidates were tried:

| route | outcome |
|---|---|
| legs for both stocks | output 0 is priced against its own feed but the router also spent on the other leg → `BelowOracleFloor` |
| legs for one stock | output 1 measures a token the router never bought → `BelowOracleFloor` |
| no legs | `NothingRouted` |

Since `MAX_OUTPUTS` is 10 and `BadWeights` enforces the weights sum, the basket feature is reachable
and advertised but dead.

**PoC** — `test/review/R04_RelayerControl.t.sol`: `test_R05_basketUnfillable_bothLegs`,
`test_R05_basketUnfillable_singleLegSet`, `test_R05_basketUnfillable_noLegs`, plus
`test_R05_control_eachStockFillsOnItsOwn`, which fills AAPL and AMZN individually to prove the
failure is `_legsFor`, not a bad venue or feed.

**Suggested fix (not applied).** Carry per-output legs — `Route { ...; Leg[][] legsPerOutput; }` —
and index them. Separately, have `PartitioRouterV2` reject a leg whose venue does not contain
`tokenOut`; that alone converts this from a silent misroute into a clear revert.

### R-06 — Medium — a short fill is booked as a full fill and the residue is stranded

`_execute` decides success from "did the call revert", never from "did it consume `amountIn`"
([`PartitioRouterV2.sol:180`](../src/v2/PartitioRouterV2.sol#L180)):

```solidity
try IUniswapV3Pool(v.target).swap(...) { ... return true; } catch { ... return false; }
...
try IPropPair(v.target).swapExactIn(...) returns (uint256 o) { ...; return o != 0; }
```

A v3 pool whose liquidity is exhausted against the price limit returns normally having consumed less
than `amountSpecified`. A propAMM pair that part-fills returns a non-zero `amountOut`. In both cases
`unfilled` stays zero, so the residue is neither re-routed by the fallback loop nor refunded at
line 166. `PartitioRouterV2` has no owner, no sweep and no rescue, and `before = balanceOf(tokenOut)`
in every later call deliberately excludes whatever is already sitting there — so the residue is
unrecoverable by anyone, including the depositor.

The oracle guard partially masks this: it is handed `total - unfilled`, i.e. the *full* leg size,
so a large short fill fails the band. A small one does not. Measured with a venue consuming 95% of
its leg and paying out enough to clear a 3% band computed on the full amount:

```
routed (USDG)      : 1000000000
pool consumed      :  950000000
stranded in router :   50000000     <- 5% of the order, no refund, no LegFailed event
AAPL out           : 2898582605788547169   <- and the swap reported success
```

This matters more than a mock usually would, because `IPropPair`'s own doc in this repo says short
filling makers are *expected*: "a reverting or short-filling maker must never brick a route."

**PoC** — `test/review/R06_RouterStranding.t.sol`:
`test_R06_v3ShortFillIsCountedAsSuccessAndResidueIsStranded` (5% stranded via v3),
`test_R06_makerShortFillStrandsTheResidue` (40% via a propAMM pair),
`test_R06_strandedResidueIsUnrecoverable` (no admin selector; a later swap cannot pick it up).
Medusa also found this independently — see §5.

**Suggested fix (not applied).** Measure consumption rather than trusting the return:

```solidity
uint256 before = IERC20(tokenIn).balanceOf(address(this));
try ... { } catch { }
uint256 used = before - IERC20(tokenIn).balanceOf(address(this));
if (used < amountIn) unfilled += amountIn - used;   // falls through to the fallback, then refunded
return used > 0;
```

That reuses the existing `unfilled` machinery, so the residue is re-routed and then refunded, and it
also fixes the guard's input (`total - unfilled` becomes the amount genuinely spent).

### R-09 — Medium — the feed is unvalidated and unbound to the tokens being traded

`OracleGuard.Params.feed` is an address taken from the caller. There is no allowlist, and nothing
ties the feed to `tokenIn`/`tokenOut`. `PartitioRouterV2.swapExactIn` is a public entry point, so
any integrator other than `GaslessEntry` gets no protection from the guard at all unless it
independently picks the right feed.

Two degrees:
- **A real but wrong Chainlink feed.** Pricing a $338 stock against a $246 feed produces a floor 27%
  too low, and a fill the correct feed rejects at a 3% band sails through.
- **An attacker-supplied contract.** The floor collapses to zero.

Inside `GaslessEntry` the feed *is* covered by the order signature (confirmed — see §4), so the
signer commits to it, which is the right design. The residual exposure is that nothing on-chain
checks the front-end picked a feed matching the asset.

**PoC** — `test/review/R09_OracleGuard.t.sol`: `test_R09_wrongFeedSilentlyLowersTheFloor`,
`test_R09_attackerSuppliedFeedMakesTheFloorZero`.

**Suggested fix (not applied).** Commit the token→feed mapping the same way venues are committed:
a second immutable Merkle root over `(token, feed)` pairs, with the proof carried in `Params`. That
keeps the ownerless property while making a wrong feed unprovable rather than merely unlikely.

### R-12 — Medium — one outstanding permit-funded order per user, and the relayer picks it

[`GaslessEntry.sol:207`](../src/v2/GaslessEntry.sol#L207) handles the permit front-run correctly —
a permit already submitted by someone else is tolerated because the allowance is re-checked. What it
does not handle is that **ERC20Permit nonces are strictly sequential**.

If a user signs two stock-selling orders, their permits carry nonces `n` and `n+1`. The relayer
chooses the fill order. Whichever it picks second is fine; whichever it picks *first* — if that is
the `n+1` order — reverts: the permit fails on the nonce, the `catch` swallows it, and
`transferFrom` then fails on a zero allowance. The signer must re-sign.

This is availability, not loss, but it is relayer-controlled and invisible to the signer.

**PoC** — `test/review/R11_Signature.t.sol`: `test_R12_secondPermitOrderIsBrickedByFillOrder`, with
`test_R12_control_oneSellOrderFills` as the control.

**Suggested fix (not applied).** Prefer `permit2` (unordered nonces) for the stock side, or document
that permit-funded orders are strictly serial and have the relayer enforce that ordering.

### R-07 / R-08 — Low — the v3 callback trusts the pool over the leaf

[`PartitioRouterV2.sol:217`](../src/v2/PartitioRouterV2.sol#L217):

```solidity
if (amount0Delta > 0) IERC20(IUniswapV3Pool(pool).token0()).safeTransfer(pool, uint256(amount0Delta));
```

- **R-07** — The venue leaf commits `token0`/`token1`, and `_execute` checks `tokenIn` against them,
  but settlement uses the pool's *self-reported* `token0()`/`token1()`. The Merkle root is therefore
  not binding on which token leaves the router. The code comment notes that up-v3 pools are EIP-1167
  clones whose addresses are not a function of the pool key, which is exactly the setting where the
  committed values should be preferred over the reported ones.
- **R-08** — The callback honours whatever delta the pool reports, with no check against the leg's
  `amountIn`. One registered venue can draw the whole call's balance.

Both require a registered (Merkle-committed) venue to misbehave, so they are trust-assumption
hardening rather than live exploits. They are cheap to close.

**PoC** — `test_R07_callbackTrustsThePoolsSelfReportedTokensNotTheLeaf` (the router pays out AMZN on
a leaf that committed USDG), `test_R08_callbackHasNoPerLegBudget` (a venue draws 10x its leg).

**Suggested fix (not applied).** Encode the leg's committed `(token0, token1, amountIn)` into the
callback `data` alongside the target, and in the callback transfer the committed token and require
`uint256(amountDelta) <= committedAmountIn`.

### R-10 / R-11 — Low — two edges of the guard's stated policy

- **R-10** — `if (block.timestamp > upd && block.timestamp - upd > MAX_AGE_SECONDS)` correctly avoids
  an underflow on a future timestamp, but the effect is that a feed reporting `updatedAt` a year in
  the future skips the dead-feed ceiling entirely. Harmless with a healthy Chainlink feed; free to
  close with an upper sanity bound.
- **R-11** — `MAX_DEV_BPS = 2000` permits a 20% haircut, and `fill` is permissionless. That is the
  most an adversarial relayer can extract on the router path while looking entirely compliant. It
  is a deliberate design ceiling rather than a bug, but it is worth stating in the same breath as
  the guard's marketing: the guard bounds catastrophe, it does not bound MEV.

**PoC** — `test_R10_futureUpdatedAtBypassesTheDeadFeedCeiling`,
`test_widestBandPermitsATwentyPercentHaircut`.

## 3. Informational

- **`GreedySplit` is imported by `PartitioRouterV2` and never called.** The deployed contract does
  no splitting at all — the split arrives fully formed in `legs`. That is consistent with the
  NatSpec ("a caller-supplied split"), but it means the "split is never worse than the best single
  venue" property tested in `test/RouterV2.t.sol` is a property of the off-chain quoter, not of the
  deployed contract. Worth stating plainly wherever that claim is made, and the dead import worth
  removing.
- **ERC-8056 `uiMultiplier`, measured across all 37 stock tokens.** 13 carry a non-unit multiplier;
  the largest is SGOV at **51.02 bps**, which already exceeds `DEVIATION_FLOOR_BPS` (50). `OracleGuard`
  never reads `uiMultiplier()`, and the convention it relies on ("prices already include the
  multiplier") is recorded only in a comment in `script/recon/chainlink-feeds.json` — not in the
  contract, not in a test. I measured pool spot against feed price for 30 tokens to check the
  direction, and **the data supports the documented convention**: dividing the multiplier out makes
  the pool/feed fit *worse* (median −13.6 bps vs −2.8 bps for the multiplier-bearing group). So no
  correction is indicated today. The point stands that a load-bearing external convention is
  asserted nowhere the compiler or the test suite can see it, and one token has already reached the
  size of the guard's own minimum band.
- **ADDENDUM 2026-09-24, uiMultiplier convention now settled decisively.** The paragraph above
  called the evidence supportive but weak. A direct measurement on SGOV — the largest multiplier at
  51.02 bps — is not weak. Executing real router fills against SGOV's deep 5 bps pool
  (`0xfAb5...1bFe` is the 3000 pool; `0x6Ba5...49b4` the 500 pool, 2576 SGOV / 149,645 USDG):

  | direction | pool fee | size | deviation vs the guard's reference |
  |---|---|---|---|
  | buy USDG→SGOV | 500 | 1,000 USDG | **0 bps** |
  | buy USDG→SGOV | 500 | 10,000 USDG | **0 bps** |
  | buy USDG→SGOV | 500 | 100,000 USDG | −8 bps |
  | sell SGOV→USDG | 500 | 10 SGOV | −10 bps |
  | buy USDG→SGOV | 3000 | 1,000 USDG | −13 bps |
  | sell SGOV→USDG | 3000 | 10 SGOV | −46 bps |

  A zero-basis-point agreement between the AMM and the feed on a liquid pool is not a coincidence.
  Had the feed been quoted per UI share — so that the guard should multiply by 1.005101770 — that
  same fill would sit 51 bps away from the correct reference, i.e. **outside the guard's own 50 bps
  DEVIATION_FLOOR_BPS**, and the tightest band the library permits could never be used on SGOV.
  The feed is priced per raw token unit and `OracleGuard` is correct as written. The residual point
  stands unchanged: nothing in the contract or the tests asserted this, which is why a regression
  test pinning the convention is now required.

- **Dust window.** Below roughly 3e9 wei of an 18-decimal stock (~1e-8 USD) the stock→USDG floor
  truncates to zero and the guard accepts any output. Economically negligible; measured rather than
  assumed (`test_dustThresholdWhereTheFloorBecomesZero`).
- **The two AAPL feeds** (`0x6B22...2cD0` used in tests, `0x4bdb...2f3f` in the recon JSON) are
  distinct proxies returning identical answers and timestamps. Not a finding; checked because a
  mismatched constant would have been one.

## 4. Checked and found clean

Each of these was attacked and held.

**Signatures and domains** (`test/review/R11_Signature.t.sol`)
- EIP-712 digest matches an independent by-hand implementation of the spec — referenced types in
  alphabetical order, `Output[]` hashed as the concatenation of member struct hashes. A wallet
  signing the displayed typed data produces a signature this contract accepts, and vice versa.
- The order hash is chain-bound and verifying-contract-bound; a second deployment cannot consume it.
- Every signed field is binding: owner, tokenIn, amountIn, maxFee, deadline, salt, output token,
  weightBps, minOut, and all three guard fields.
- Malleated `(s, v)` is rejected outright by OZ 5.1 `ECDSA` (`ECDSAInvalidSignatureS`).
- The EIP-3009 authorization is payee-bound *and* nonce-bound to the order hash: an outsider
  replaying it directly against USDG reverts, and a second `GaslessEntry` cannot use it either.
- `executed[oh]` is set before the ECDSA check, which is safe — a bad signature reverts the write.
- `ECDSA.recover` is called before `_pullIn`, so `o.owner` in the `transferFrom` is the signer, not
  an arbitrary address (already pinned by the repo's own
  `test_cannotPullFromAVictimWithAStandingAllowance`).

**Merkle venue proofs**
- Leaves are double-hashed (`keccak256(bytes.concat(keccak256(abi.encode(v))))`), so a 32-byte leaf
  preimage can never be confused with a 64-byte internal node. No second-preimage path.
- `abi.encode(h, p)` for two `bytes32` is byte-identical to `abi.encodePacked`, so the sorted-pair
  verification is OpenZeppelin-compatible.
- `Venue` is all static types and is copied calldata→memory before hashing, so the leaf is canonical
  and not malleable.
- An unregistered venue is rejected however well-formed (repo's `test_unregisteredVenueRejected`).

**Callbacks and reentrancy**
- `uniswapV3SwapCallback` is not callable outside a swap (transient `T_EXPECTED` is zero) and the
  `data`-encoded pool must equal `msg.sender`.
- `unlockCallback` requires both `msg.sender == poolManager` and the in-flight transient flag.
- Both contracts carry transient-storage reentrancy guards; `fill` is `nonReentrant` and the router's
  `swapExactIn` is too, so a token or aggregator callback cannot re-enter either.
- Aggregator approvals are set to exactly `spendable` and reset to zero on **both** the success and
  the failure path (the call is a low-level `call`, so a revert does not skip the reset).
- The aggregator allowlist is immutable and rejects `address(0)`; an unlisted target reverts.
- Neither contract exposes `owner()`, `setOwner`, `pause`, `upgradeTo`, `sweep` or `rescue`.

**Oracle guard mechanics** (`test/review/R09_OracleGuard.t.sol`)
- `answer <= 0` → `FeedBadAnswer`; `updatedAt == 0` → `FeedNeverUpdated`.
- The 120h dead-feed boundary is exact: 120h passes, 120h+1s reverts.
- Band floor (50) and ceiling (2000) are enforced at both edges.
- Decimals scaling is exact in both directions across 6/18 tokens and feed decimals 0–18, verified
  against an independently computed rational value — **256 fuzz runs, zero drift**.
- The floor truncates downward only, so rounding can favour the fill by at most one wei —
  **256 fuzz runs**.

**Tool:** Medusa 1.5.1 (installed for this review via Homebrew), property mode, cheatcodes enabled
so the harness can sign orders with `vm.sign`.

**Harness:** `test/fuzz/PartitioProps.sol` + `test/fuzz/FuzzMocks.sol`. Self-contained — a mock USDG

priced off the same feed the guard reads with fuzzer-settable slippage and fill ratio, and an

**Two honest caveats about this campaign.**
1. Medusa's `stopOnFailedTest` defaults to **true**, and the config key lives at
   `fuzzing.testing.stopOnFailedTest`, not `fuzzing.stopOnFailedTest`. Placed at the wrong level it
   is silently ignored and the campaign halts on the first failure after a few seconds. Three
   earlier runs of this harness reported "1 failed" for exactly that reason. The numbers above are
   from the corrected config (`medusa.json`), which is committed.
2. `h_setFill` is deliberately shaped to 90–100% of the leg. A 50% short fill is rejected by the
   oracle band and never reaches the stranding path, so an unshaped range mostly explores a revert.
   The shaping is documented in the harness; it narrows the search to the case that actually slips
   past the guard.

## 6. Not covered — stated plainly

- **The Stylus `PartitioMath` contract is not in the trust surface at all.** The brief names it "as
  used", but `grep -rniE 'stylus|partitiomath' src/` returns nothing: neither `PartitioRouterV2` nor
  `GaslessEntry` references it. It is deployed on 4663 and benchmarked in `docs/STYLUS.md`, but no
  reviewed contract calls it, so there was nothing to attack. If that changes, it needs its own pass.
- **The v4 leg was not attacked.** `unlockCallback`'s `sync`/`settle`/`take` accounting, the
  `BalanceDelta` sign handling and hook-bearing pool keys were read but not exercised adversarially.
  The repo's `test/V4Exec.t.sol` covers the happy path only. This is the largest untested surface.
- **The real Kyber router's calldata surface.** R-02 is demonstrated with a mock that models the
  capability — an allowlisted aggregator taking its destination from relayer-chosen calldata. I did
  not construct a live `MetaAggregationRouterV2` route, so R-02 establishes that the code path has
  no oracle check; it does not establish which specific Kyber selector expresses it. The fix is the
  same either way.
- **Real Rialto propAMM pairs** were modelled with a mock for the same reason.
- **Upgradeability.** USDG is a diamond and the stock tokens are beacon proxies. A beacon or facet
  upgrade can change token semantics under both contracts — balance behaviour, transfer hooks, the
  `isBlocked` gate visible in traces. Not analysed.
- **Gas/DoS via `legs.length`.** `swapExactIn` iterates the legs array up to three times with no
  bound. Not quantified.
- **No symbolic execution or formal verification** (no Halmos, no Certora, no Echidna — Medusa only).
- **Slither was not run** here; the repo carries a `.venv-sec` with it, and Medusa warned it could
  not find `slither` on PATH during the campaign, which does not affect the property results.
- **No economic/MEV modelling** of the split algorithm, and no live-chain transactions of any kind:
  everything is fork-local, no keys were used, nothing was broadcast.
